# Phase 8.1.4 — Semantic Evidence Support

## 1. Problem Statement

Phase 8.1.3 established a deterministic, role-aware grounding layer requiring query Subject concepts to have grounded evidence in candidate code units. While this successfully eliminated the RBAC false positive and fixed morphological issues (e.g. plural `months`), **strict exact lexical matching remained too restrictive when a repository expresses a concept using different vocabulary**.

For example:
- Query: `How does the application authenticate users?`
- Repository symbols: `LoginService`, `SessionManager`, `TokenValidator`, `IdentityProvider`.
- The repository genuinely implements authentication, but literal substring `"authenticate"` may not occur in symbol names or file paths.

---

## 2. Distinction: Candidate Discovery vs. Evidence Validation

A crucial architectural distinction governs Phase 8.1.4:

```text
Semantic Retrieval (SemanticRetriever)
    =
Candidate Discovery (Which retrieval units in the repository are closest to the full query?)

Semantic Evidence Support (SemanticEvidenceSupport)
    =
Evidence Validation (Does this specific retrieved evidence semantically support a query Subject concept?)
```

`SemanticEvidenceSupport` does **not** re-search the repository or replace the Phase 6 retrieval pipeline. Instead, it operates during evidence evaluation on retrieved candidates, validating whether candidate representations semantically ground individual Subject concepts.

---

## 3. Existing Embedding Representation

Investigation of the MiniLM embedding infrastructure revealed:
1. **RetrievalUnit Embedding Text**: Generated by `SemanticTextFormatter::format_unit(unit)`:
   - Language, file path, kind, parent context, name, detail.
   - Structured supporting AST evidence summaries: `Calls: ...` (up to 5), `Renders: ...` (up to 4), `Attributes: ...` (up to 4).
   - Source bodies are intentionally excluded to keep embedding representations compact and high-signal without noise.
2. **Reusability**: Candidates in the `EvidenceBundle` have `primary_element_id()`. Precomputed unit embeddings in `SemanticIndex` are looked up in $O(1)$ time without recomputing candidate vectors.
3. **Concept-level embedding**: Individual query Subject concepts (e.g. `"authentication"`) are embedded independently via `EmbeddingProvider::embed(concept)` into 384-dimensional dense vectors.

---

## 4. Concept-Level Semantic Matching Strategy

Rather than comparing the entire conversational query string against repository code, `SemanticEvidenceSupport` isolates the **Subject concepts** identified during Query Understanding:

```text
Query: "Where is user authentication handled?"
        ↓
Query Understanding:
  Subject: ["authentication"]
  Action:  ["handle"]
  Context: ["where", "is", "user"]
        ↓
Embedding: embed("authentication")
        ↓
Cosine similarity against candidate embeddings (LoginService, SessionManager, etc.)
```

This prevents generic interrogatives (`where`, `how`, `is`) and inquiry verbs (`implemented`, `handled`, `defined`) from corrupting semantic similarity calculations.

---

## 5. Multi-Signal Evidence Evaluation & Semantic Coherence

To prevent isolated coincidences (such as generic search engines having ~0.70 similarity to unrelated acronyms) from establishing false sufficiency, `SemanticEvidenceSupport` evaluates multiple reinforcing signals:

1. **Lexical / Substring Presence**: Exact or stemmed matches in symbol names, file paths, or excerpts provide baseline 1.0 support.
2. **Structural Reinforcement**: Cross-file relationship edges, calls, or parent contexts referencing the concept reinforce candidate credibility.
3. **Multi-Candidate Reinforcement (Coherence)**:
   - When $\ge 2$ distinct candidates exhibit strong semantic similarity ($\ge 0.65$) to a concept, their mutual reinforcement produces a high coherent support score:
     $$S_{\text{coherent}} = 0.5 \cdot S_{\text{top}} + 0.5 \cdot S_{\text{top2}}$$
   - When only 1 candidate matches without structural confirmation, the score is penalized to prevent isolated false positives:
     $$S_{\text{coherent}} = S_{\text{top}} \cdot 0.65$$

---

## 6. Integration with EvidenceSufficiencyChecker

`EvidenceSufficiencyChecker` remains the final deterministic gatekeeper:

```text
Query
 ↓
QueryUnderstanding
 ↓
PrimaryRetrievalPipeline (Lexical + Semantic)
 ↓
EvidenceAssembler (Source snippets + Graph relationships)
 ↓
EvidenceBundle
 ↓
SemanticEvidenceSupport (Subject embeddings + Candidate lookup)
 ↓
EvidenceSufficiencyChecker (Deterministic policy gate)
 ↓
ContextBuilder → ReasoningService → Local LLM / Refusal
```

A Subject concept is grounded if it has **either** lexical support **or** coherent semantic evidence support.

## 8. Performance & Latency

- **Concept Embedding Overhead**: ~2–5 ms per Subject concept (1–2 concepts per typical query).
- **Candidate Lookup**: $O(1)$ in-memory hash table lookup in `SemanticIndex` (0 ms candidate recomputation).
- **Total Evidence Evaluation Time**: 5–15 ms repository-wide.

---

## 9. Known Limitations & Architectural Invariants

> **Core Principle**: Embeddings discover semantic relationships; they do not prove repository truth.

1. **Candidate Retrieval Dependency**: If primary retrieval fails to bring any related candidates into the top-K window (e.g. due to severe vocabulary divergence across large repos), semantic evidence support cannot evaluate them.
2. **Ambiguous Synonyms**: Words with polysemous meanings in programming (e.g. `state` vs. `status`, `driver` vs. `handler`) require multi-candidate reinforcement to disambiguate reliably.
